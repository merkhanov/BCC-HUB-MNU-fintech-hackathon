# Сценарий демонстрации

Сценарий для видео работы агента и для защиты в финале. Запись занимает 4 или 5 минут. Каждый шаг привязан к критерию жюри: уточнение, архитектура, ценность, презентация.

## Подготовка

1. Склонируйте репозиторий, выполните `bun install` и впишите ключ в `.env` (README, разделы 2 и 3).
2. Сделайте прогон заранее, до записи. Живой прогон длится от 3 минут до часа, в зависимости от загрузки Gemini, поэтому на записи лучше показать готовый результат и короткий повтор из кэша:

   ```bash
   bun start docs/requirements.md reports/demo.report.md
   ```

   Повторный запуск той же команды возьмёт все ответы из кэша и закончится за секунду. Лог при этом показывает те же шаги.
3. Откройте в редакторе `docs/requirements.md`, `reports/demo.report.md` и `reports/demo.report.questions.md`.
4. Увеличьте шрифт терминала. Лог агента пишется в stderr без цвета.

Если на записи нет сети или ключа, покажите тот же путь на тестовых данных: `LLM_PROVIDER=fixture FIXTURE_DIR=test/fixtures/llm bun start test/fixtures/sample.md /tmp/sample.report.md --ask`. Отчёт тогда помечен как «Тестовый прогон», скажите об этом вслух.

## Ход записи

### 1. Задача, 20 секунд

Покажите `docs/requirements.md`. Скажите, что агент делает ревью требований до разработки по ISO/IEC/IEEE 29148 и IEEE 830, находит дефекты формулировок и задаёт автору вопросы, без которых документ нельзя отдать в разработку.

### 2. Запуск одной командой, 40 секунд. Критерий «Архитектура»

```bash
bun start docs/requirements.md reports/demo.report.md
```

Пока идёт лог, покажите шаги: нарезка, проверка требований пакетами по 8, проверка набора, сверка пар, уточняющие вопросы. Скажите, что у каждого шага своя роль и своя схема ответа, а код проверяет результат каждого шага. Покажите схему в README, раздел 5.

### 3. Вопросы автору, 60 секунд. Критерий «Уточнение»

В конце лога агент печатает пять главных вопросов. Затем откройте раздел 7 отчёта:

- вопрос адресован конкретной роли: бизнесу, аналитику, архитектору, тестированию;
- у вопроса есть причина, варианты ответа и место в документе;
- вопрос объединяет несколько находок, на которые отвечает один ответ;
- вопросы по критичным дефектам идут первыми.

Скажите, что код отбрасывает вопрос, если он не ссылается на настоящую находку. Поэтому в списке нет общих вопросов вида «уточните требование».

### 4. Ответы и повторная проверка, 60 секунд. Критерий «Уточнение»

```bash
bun start docs/requirements.md reports/demo.report.md --ask
```

Ответьте на два или три вопроса: один цифрой варианта, один своим текстом, один пропустите Enter. Агент сохранит ответы и спросит, проверить ли документ заново. Если времени на живой повтор нет, ответьте «n» и покажите команду с `--answers`, которую агент напечатал. Если повтор сделан заранее, покажите в его отчёте паспорт с числом ответов и таблицу «Учтённые ответы автора» в разделе 7.

### 5. Отчёт, 60 секунд. Критерий «Ценность»

Пройдите по отчёту сверху вниз:

1. Паспорт: модель, дата, коммит агента, число запросов к API.
2. Нарезка: свои номера ТР-NN, номера документа и место каждой цитаты.
3. Одна находка: возьмите её цитату и найдите в документе по номеру строки. Покажите, что цитата дословная.
4. Противоречие в разделе 4 с цитатами обоих мест.
5. Сводка и итог: «начинать нельзя», число критичных дефектов, что исправить первым.
6. Приложение «Отклонённые находки», если оно есть. Скажите, что агент не верит модели на слово: находку без цитаты из документа он не считает.

### 6. Надёжность, 20 секунд. Критерий «Архитектура»

Покажите в логе повтор после 503 или переход на резервную модель, если они были. Скажите, что у каждого запроса срок 5 минут, что дневная квота переключает модель сразу и что упавший прогон продолжается из кэша.

### 7. Тесты и сверка, 30 секунд

```bash
bun test
```

38 тестов без сети и ключа. Они проверяют поиск цитат в MD, PDF и DOCX, отклонение выдуманных цитат, резервную модель, срок ответа, вопросы, возврат ответов и вывод `--json`.

Затем покажите `bun run recall`: сданный отчёт нашёл 11 из 12 известных дефектов документа, прогон на Flash-Lite 7 из 12. Скажите, что список дефектов промпты не видят, он нужен только для оценки.

## Вопросы жюри и ответы

| Вопрос | Ответ |
| --- | --- |
| Почему не один промпт на весь документ? | Один запрос пропускает требования. Пакеты по 8 дают проверить каждое требование по каждому критерию, а пропущенное агент переспрашивает |
| Как вы боретесь с галлюцинациями? | Каждая цитата ищется в документе кодом. Находку без цитаты агент отклоняет и показывает в приложении. Вопрос без ссылки на находку отбрасывается |
| Кто решает, что дефект критичный? | Код по правилу: высокая серьёзность, или средняя по проверяемости, полноте и непротиворечивости. Итог тоже считает код |
| Модель недетерминирована. Как сравнивать прогоны? | `bun run recall` сверяет отчёт с 12 известными дефектами документа: Flash нашла 11, Flash-Lite 7. Числа находок между прогонами Flash отличаются на 10 или 15 процентов. Результаты в README, раздел 7. Кэш позволяет повторить конкретный прогон |
| Что если Gemini недоступен? | Повторы с паузой, резервная модель, срок 5 минут на запрос, продолжение из кэша. Есть OpenAI-совместимый провайдер для Ollama или другого API |
| Почему вы не подсказали модели дефекты этого документа? | Промпты содержат общие приёмы ревью и примеры из другой области. Агент должен работать на любом ТЗ |
| Чем агент полезен банку? | Аналитик получает список дефектов с местами и готовые вопросы к заказчику до начала разработки. Дефект, найденный в ТЗ, дешевле дефекта, найденного в тестировании или в продакшене |
