- Почему важно: Использование GET для сохранения нарушает стандарты REST API, а отсутствие метода чтения делает невозможным получение текущих настроек мобильным приложением.
- Варианты ответа: 1) 1) POST /alerts/saveLimit для сохранения, GET /alerts/getLimit для чтения; 2) 2) PUT /alerts/saveLimit для сохранения, GET /alerts/saveLimit для чтения; 3) 3) POST /alerts/saveLimit с параметрами в Request Body
- Места: «**Description** Сохранение порога. Функциональные требования: чтение порога» (строка 103); «**REST type** GET» (строка 104); «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API». Повторная доставка одного события процессинга сохраняет исходный итог.» (строка 52)
- Из находок: Н-01; ТР-12, Корректность; ТР-16, Корректность; ТР-17, Уместность уровня; ТР-33, Корректность; ТР-34, Уместность уровня

#### В-02. Архитектору, по критичному дефекту

#### В-06. Бизнес-заказчику, по критичному дефекту

**Если клиент уже получил push-уведомление в текущем месяце, а затем изменил порог на новое значение, которое ниже текущих расходов за месяц, следует ли отправлять повторный push?**

- Почему важно: Противоречие между лимитом 1 push в месяц (Ф-3) и правилом реактивации при смене порога (Ф-4) приведет к некорректной работе уведомлений.
- Варианты ответа: 1) 1) Отправлять push повторно при достижении/превышении нового порога; 2) 2) Не отправлять push, строго соблюдая лимит не более 1 push в календарный месяц; 3) 3) Отправлять push сразу в момент сохранения нового порога
- Места: «Ф-3. Когда расходы переходят от суммы ниже порога к сумме, равной порогу или выше, клиент получает push. На карту приходится максимум один такой push за календарный месяц.» (строка 39); «Ф-4. При изменении порога накопленная сумма сохраняется. Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.» (строка 40)
- Из находок: Н-03; ТР-08 (Ф-4), Полнота

#### В-08. Тестированию, по критичному дефекту
