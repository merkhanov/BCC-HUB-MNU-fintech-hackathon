#### В-01. Архитектору, по критичному дефекту

**Почему для сохранения настроек порога используется метод GET, который не должен изменять состояние системы на сервере?**

- Почему важно: Использование GET для изменения данных нарушает стандарты REST API и архитектурные принципы идемпотентности, что приведет к ошибкам интеграции.
- Варианты ответа: 1) 1) использовать метод POST для изменения настроек; 2) 2) использовать метод PUT для замены настроек; 3) 3) оставить GET для получения и сохранения параметров
- Места: «REST type GET» (строка 104); «При отклонении суммы вернуть прежнее состояние и результат ERROR.» (строка 121); «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API». Повторная доставка одного события процессинга сохраняет исходный итог.» (строка 52)
- Из находок: Н-01; ТР-24, Корректность; ТР-19, Однозначность; ТР-23, Однозначность

#### В-02. Бизнес-заказчику, по критичному дефекту

**Какому месяцу принадлежит покупка, совершенная 31 января и проведённая 1 февраля: январю по дате совершения (Ф-2) или февралю по дате проведения (критерий приёмки)?**

- Почему важно: Разные трактовки приведут к несовпадению логики расчёта месячных расходов в коде сервиса и в приёмочных тестах.
- Варианты ответа: 1) 1) январю по дате совершения покупки в Алматы; 2) 2) февралю по дате проведения процессингом; 3) 3) месяцу фиксации проводки в системе учёта
- Места: «Ф-2. Месяц определяется по дате совершения покупки в Алматы. В расходы входят проведённые покупки. Возврат уменьшает расходы месяца исходной покупки. Переводы и снятие наличных исключаются.» (строка 38); «Покупка 31 января в 23:58 на 4 000 ₸ Провести 1 февраля в 00:03 по Алматы Февральский счётчик вырос на 4 000 ₸» (строка 64)
- Из находок: Н-04; ТР-21, Проверяемость

#### В-03. Бизнес-заказчику, по критичному дефекту

**Должна ли система отправить второй push в текущем календарном месяце, если лимит был изменен, или ограничение «максимум один push в месяц» из Ф-3 является абсолютным?**

- Почему важно: Без ответа разработчик не сможет реализовать логику отправки уведомлений при изменении лимита, а тестировщик не сможет составить тест-кейс для проверки конфликта правил Ф-3 и Ф-4.
- Варианты ответа: 1) 1) отправить второй push при повторном достижении нового порога; 2) 2) не отправлять второй push, так как лимит один на календарный месяц; 3) 3) отправлять push только при увеличении порога
- Места: «Ф-3. Когда расходы переходят от суммы ниже порога к сумме, равной порогу или выше, клиент получает push. На карту приходится максимум один такой push за календарный месяц.» (строка 39); «Ф-4. При изменении порога накопленная сумма сохраняется. Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.» (строка 40)
- Из находок: Н-03; ТР-15 (Ф-4), Однозначность

#### В-04. Архитектору, по критичному дефекту

- Варианты ответа: 1) 1) добавить поле типа операции в требования к данным; 2) 2) фильтровать операции на стороне карточного процессинга до передачи; 3) 3) определять тип по диапазону идентификатора операции
- Места: «Переводы и снятие наличных исключаются.» (строка 38); «Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге.» (строка 49)
- Из находок: Н-02

- Места: «Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге.» (строка 49)
- Из находок: Н-05

- Места: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.» (строка 23)
- Из находок: ТР-08, Проверяемость

#### В-10. Аналитику, по критичному дефекту

**Какую ветку процесса выполняет система, если в результате покупки порог не оказывается достигнутым?**

- Почему важно: Отсутствие описания альтернативной ветки процесса не позволяет запрограммировать поведение системы при невыполнении условия порога.
- Варианты ответа: 1) 1) завершение процесса без отправки push-уведомления; 2) 2) отправка информационного сообщения о текущем остатке до порога; 3) 3) сохранение суммы в буфер до конца дня
- Места: «Проведение покупки → пересчёт расходов → проверка порога → при достижении отправка push → завершение.» (строка 34)
- Из находок: ТР-11, Проверяемость

- Из находок: ТР-16, Полнота
