- Места: «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.» (строка 23)
- Из находок: ТР-08, Проверяемость

#### В-10. Архитектору, по критичному дефекту

**Какие протоколы (HTTP/REST, gRPC, очереди сообщений) используются для взаимодействия между мобильным приложением, сервисом настроек, карточным процессингом, учётом расходов и сервисом push?**

- Почему важно: Без указания протоколов и форматов обмена между компонентами невозможно спроектировать интеграционные контракты.
- Варианты ответа: 1) Использовать REST/HTTP для синхронных вызовов и брокер сообщений для событий процессинга; 2) Использовать исключительно очереди сообщений для всех компонентов; 3) Свой вариант
- Места: «Мобильное приложение → сервис настроек. Карточный процессинг → учёт расходов → сервис push.» (строка 26)
- Из находок: ТР-09, Проверяемость

#### В-11. Архитектору, по критичному дефекту

**Каково поведение системы на схеме процесса, если отправка push-уведомления сервисным слоем завершилась ошибкой?**

- Почему важно: Невозможно реализовать обработку исключений и повторные попытки (retry) при сбое отправки push.
- Варианты ответа: 1) Повторить отправку push асинхронно через заданный интервал; 2) Завершить процесс без повторной отправки уведомления; 3) Свой вариант
- Места: «Проведение покупки → пересчёт расходов → проверка порога → при достижении отправка push → завершение.» (строка 34)
- Из находок: ТР-11, Полнота

#### В-12. Архитектору, по критичному дефекту

**Как сервис расходов должен реагировать на сбой или таймаут при запросе порога карты из сервиса настроек?**

- Почему важно: При отсутствии сценария обработки тайм-аута или ошибки сервиса настроек поведение при транзакции останется неопределенным.
- Варианты ответа: 1) Пропускать проверку порога и не отправлять push; 2) Повторять запрос к сервису настроек до успешного ответа; 3) Свой вариант
- Места: «Процессинг → сервис расходов: проведена покупка. Сервис расходов → настройки: получить порог карты. Сервис расходов → push: передать последние четыре цифры карты и сумму при достижении порога.» (строка 43)
- Из находок: ТР-16, Полнота

#### В-13. Архитектору, по критичному дефекту

**Какую долю успешных отправлений (процентиль) нужно учитывать при замере интервала в одну минуту и от какой токи в системе начинается отсчет?**

- Почему важно: Невозможно составить автотесты и проверить нефункциональное требование без точной точки отсчета и порогового процентиля.
- Варианты ответа: 1) Отсчет от момента регистрации события в сервисе расходов, 95% запросов за 1 минуту; 2) Отсчет от получения запроса сервисом push, 100% запросов за 1 минуту; 3) Свой вариант
- Места: «Сервис передаёт push на отправку в течение минуты после получения события.» (строка 46)
- Из находок: ТР-17, Проверяемость

#### В-14. Архитектору, по критичному дефекту

**Какие типы данных и ограничения длины/формата имеют поля «идентификатор карты», «месяц», «идентификатор операции», «сумма покупки в тиынах», «признак отправки» и «порог в тенге» при сохранении в базе данных?**

- Почему важно: Разработчик базы данных не сможет создать таблицы и корректно настроить маппинг сущностей без детальной спецификации полей хранения.
- Варианты ответа: 1) Использовать типы данных по умолчанию согласно стеку реализации; 2) Зафиксировать типы данных в соответствии с параметрами API и процессинга; 3) Свой вариант
- Места: «Хранить идентификатор карты, месяц, идентификатор операции, сумму покупки в тиынах, признак отправки и порог в тенге.» (строка 49)
- Из находок: ТР-18, Полнота

#### В-15. Аналитику, по критичному дефекту

**По каким критериям проверяется пользовательская сессия на шаге 1 и какие данные сессии сверяются?**

- Почему важно: Без критериев проверки сессии невозможно запрограммировать валидацию токена и написать корректные тест-кейсы для авторизации.
- Варианты ответа: 1) Проверка валидности Bearer-токена через сервис авторизации и сверка идентификатора владельца; 2) Проверка наличия активной сессии в базе данных; 3) Свой вариант
- Места: «1. Проверить пользовательскую сессию.» (строка 117)
- Из находок: ТР-29, Проверяемость

#### В-16. Аналитику, по критичному дефекту

**Какому формату или регулярному выражению должен соответствовать идентификатор карты cardId длиной 1–64 символа?**

- Почему важно: Без паттерна валидации входного параметра cardId невозможно реализовать проверку на уровне API и защитить сервис от некорректных запросов.
- Варианты ответа: 1) Любые символы длиной от 1 до 64 символов без ограничений по алфавиту; 2) Только буквенно-цифровые символы и дефисы; 3) Свой вариант
- Места: «cardId string 1–64 Да Карта клиента Идентификатор карты card_id» (строка 142)
- Из находок: ТР-38, Полнота
